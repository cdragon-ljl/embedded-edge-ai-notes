本节回答两个问题：**其一**，AI 基础设施的底层开发究竟在做什么，它与嵌入式系统开发在方法论上是否存在同构关系；**其二**，一条从 CUDA 出发、最终落在 NPU 算子开发与端侧 AI 部署的完整学习路径应当如何设计。

## 1. AI 底层的本质：高性能计算问题

### 1.1 算子的定义

**定义 1（算子, Operator）**：神经网络中可独立优化、被高频调用的基本运算单元，如矩阵乘法（MatMul）、归一化（LayerNorm/RMSNorm）、Softmax、激活函数（ReLU/GELU）等。深度学习模型可视为算子构成的计算图；模型性能的上限，由图中每个算子的实现效率决定。

### 1.2 为什么需要手工实现算子

PyTorch 等框架虽内置常用算子，但工程实践中仍需要算子开发者手工实现，原因有三：

1. **性能**：框架默认实现未必最优。同一矩阵乘法，朴素 CUDA 实现与高度优化的 cuBLAS 之间可相差数十倍，差距来自访存调度、指令级并行、硬件特化等多层次优化；
2. **融合（Fusion）**：将多个算子合并为单个 kernel，避免中间结果反复写回全局内存。例如"GELU + LayerNorm + MatMul"融合可省去两次全局内存往返，推理延迟可降低 20%~50%（具体数值依模型与硬件而定）；
3. **定制**：新模型结构出现时，框架尚无对应实现，必须自行编写高性能版本。

### 1.3 嵌入式背景的适配性

表 1-1 给出嵌入式系统开发与算子开发的工作对照：

| 嵌入式工程师日常工作 | 算子开发者日常工作 |
|:---|:---|
| 依据 datasheet 配置寄存器 | 依据 CUDA 手册调用 API |
| 优化 DMA 搬运，减少 CPU 等待 | 优化显存搬运，减少 kernel 等待 |
| 以 Cache 命中率评估代码 | 以 Occupancy / 带宽利用率评估代码 |
| 位运算、内存池、环形缓冲 | Bank Conflict、Shared Memory、Warp 调度 |
| 代码运行于 72 MHz MCU | 代码运行于数千 CUDA 核心 |

可见二者在"硬件感知力"上高度同构：**换的是硬件平台，不换的是思维方法**。这是本系列以嵌入式工程师为读者画像的根本依据。

## 2. GPU 与 CPU/MCU 的架构差异

### 2.1 设计哲学对比

CPU/MCU 的设计哲学为**少而强**：以少量复杂核心（分支预测、乱序执行、大容量缓存）追求单线程性能。GPU 的设计哲学为**多而弱**：以数千个精简核心追求总吞吐量，适合简单、重复、数据并行的任务。

设任务量为 100 万个独立元素的滤波运算：MCU 以单核心串行迭代 100 万次；GPU 以 4608 个核心并行分摊，理论上每核心处理约 217 个元素。吞吐量的数量级差异来自并行规模。

### 2.2 数量级对比

表 2-1 列出三个代表性平台的硬件指标（5060 Ti 数值以 deviceQuery 实测为准）：

| 指标 | STM32F407 | 主流桌面 CPU | RTX 5060 Ti |
|:---|:---:|:---:|:---:|
| 核心数 | 1 | 8~16 | 4608 CUDA Core |
| 主频 | 168 MHz | 3~5 GHz | ≈2.5 GHz |
| 内存/显存 | 192 KB SRAM | 16~32 GB DDR5 | 8 GB GDDR7 |
| 内存带宽 | ≈400 MB/s | ≈60 GB/s | ≈448 GB/s |

内存带宽的差异是关键：GPU 以超过 1000 倍于 MCU 的带宽供给数千个核心，这是其吞吐量优势的物理基础。

### 2.3 本系列目标硬件：RTX 5060 Ti

本系列主线基于 RTX 5060 Ti 8GB（GB206-300，Blackwell 架构，sm_120），关键参数如下（以 deviceQuery 实测为准）：

- CUDA 核心：4608 个（36 SM × 128）
- Tensor Core：144 个（第五代）
- 显存：8 GB GDDR7，128-bit
- 显存带宽：约 448 GB/s
- 计算能力：12.0（sm_120）
- 软件要求：驱动 R570+，CUDA Toolkit 13.x（12.x 不支持 sm_120）

可将 GPU 视作一块"外设"：显存对应 SRAM，带宽对应总线，核心对应算力引擎。MCU 上的存储与总线管理经验在此以更大的数量级复现。

## 3. 嵌入式工程师的三项可迁移能力

### 3.1 内存管理直觉

CUDA 编程要求显存显式管理：`cudaMalloc` / `cudaMemcpy` / `cudaFree` 分别对应 `malloc` / `memcpy` / `free` 的 GPU 版本。数据流为：分配显存 → 搬入数据 → 启动 kernel → 搬回结果 → 释放显存。

```cuda
float *d_a, *d_b, *d_c;
cudaMalloc(&d_a, n * sizeof(float));
cudaMalloc(&d_b, n * sizeof(float));
cudaMalloc(&d_c, n * sizeof(float));

cudaMemcpy(d_a, h_a, n * sizeof(float), cudaMemcpyHostToDevice);
cudaMemcpy(d_b, h_b, n * sizeof(float), cudaMemcpyHostToDevice);

myKernel<<<grid, block>>>(d_a, d_b, d_c);

cudaMemcpy(h_c, d_c, n * sizeof(float), cudaMemcpyDeviceToHost);
cudaFree(d_a); cudaFree(d_b); cudaFree(d_c);
```

嵌入式工程师具备的内存池、对齐、生命周期、双缓冲经验，在此直接迁移。这是非底层背景开发者较难逾越的第一道门槛。

【图3：Host–Device 数据流】

│   h_b ────────┼────────▶│                    │         │              │

### 3.2 带宽与访存思维

嵌入式优化的核心命题"瓶颈在数据搬运"在 GPU 上以更极端的形式出现：

- **访存合并（Coalesced Access）**：相邻线程访问相邻地址，硬件以 128 字节为粒度合并搬运，等价于 DMA 的连续突发传输；
- **Bank Conflict**：共享内存按 Bank 组织，多线程同 Bank 访问串行化，等价于多外设总线竞争；
- **Shared Memory**：SM 内片上存储，需手动管理，等价于 MCU 片上 SRAM 的手动规划。

已有"为什么必须优化访存"的信念，只需学习 GPU 上的优化工具，无需重新建立动机。

### 3.3 C/C++ 功底

CUDA kernel 以 C++ 超集编写。典型的 kernel 结构为"索引计算 + 边界判断 + 元素操作"：

```cuda
__global__ void vectorAdd(float *a, float *b, float *c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        c[i] = a[i] + b[i];
    }
}
```

串行循环 `for (i = 0; i < n; i++)` 被 GPU 硬件拆分为并行线程，`i` 由 `blockIdx/blockDim/threadIdx` 计算。指针、位运算、内存布局、编译优化等既有技能全部复用。

## 4. 目标方向：NPU 算子开发与端侧 AI 部署

### 4.1 为什么落点不是云端 GPU

对嵌入式工程师而言，职业路径的最优落点并非云端 GPU 算子（该领域竞争激烈且与硬件背景耦合弱），而是 **NPU 算子开发与端侧 AI 部署**——这正是国产 AI 芯片（瑞芯微、地平线、算能、寒武纪等）软件栈团队的核心需求：懂硬件 + 会 C++ + 能优化。

GPU（CUDA）在本系列中的定位是**思维训练场**：资料丰富、上手门槛低，用于建立并行编程、访存优化、性能模型的通用方法论；这些方法论随后迁移到 NPU（以 RK3588 + RKNN 为例），完成落地。

## 5. 硬件与软件准备

### 5.1 显存容量评估

8 GB 显存对算子开发学习**完全够用**：算子开发本质是"编写函数 + 测量性能"，对容量要求低，对带宽与核心数量要求高；5060 Ti 的 448 GB/s 带宽在甜品级显卡中属前列。

### 5.2 软件环境要求

Blackwell（sm_120）要求 CUDA Toolkit 13.x 及以上（12.x 不识别 sm_120）、驱动 R570+。NPU-02 将给出完整的环境搭建流程。

# 性能调优：帧率、延迟、CPU 与内存的全面优化

> 系列：RKNN 端侧部署实战：基于 RV1126 的模型转换与部署
> 前置：已跑通摄像头 → NPU 全链路 demo
> 配套硬件：RV1126 开发板 + 摄像头

## 0. 本节目标

demo 能跑（可能 8~10fps），产品要稳（25fps+、延迟低、CPU 有余量、内存不涨）。本节把性能调优拆成四条线：

1. **NPU 侧**：确认 NPU 真的在干活、干得快；
2. **CPU 侧**：负载均衡、核绑定、减少不必要的计算；
3. **架构侧**：多线程流水线（取流/推理/显示解耦）；
4. **测量方法**：没有数据就没有优化——先学会科学测量帧率和延迟。

## 1. 先测量：没有数据就没有优化

### 1.1 三个指标

| 指标 | 定义 | 目标参考（RV1126 + YOLOv5s INT8） |
|:---|:---|:---|
| 帧率 FPS | 每秒处理的帧数 | 产品需求而定（IPC 常见 25/30） |
| 端到端延迟 | 从"帧到达"到"结果可用"的时间 | 越低越好（实时告警场景敏感） |
| CPU 占用 | 四核的负载情况 | 留出余量给网络/编码 |

### 1.2 测量方法

```bash
# CPU 占用（板端）
top -d 1

# 各线程占用
top -H -d 1

# 帧率：在推理线程打印每秒处理帧数（每 100 帧统计一次）
```

```c
// 帧率统计（放在推理循环里）
static int frame_cnt = 0;
static struct timespec last_t;
frame_cnt++;
double now = time_ms();
if (now - last_t_ms > 1000) {
    printf("FPS: %.1f\n", frame_cnt * 1000.0 / (now - last_t_ms));
    frame_cnt = 0; last_t_ms = now;
}
```

**原则**：每次优化只改一个变量，重新测量，记录数据。调优报告 = 优化项 + 前后数据。

## 2. NPU 侧优化

### 2.1 确认 NPU 使用率

RV1126 的 NPU 使用率可以通过 SDK 提供的方式查看（或采样 `/sys` 相关节点、用官方 profiling 工具，具体以 SDK 文档为准）。调优第一步：**确认瓶颈是不是 NPU**。

判断方法：把推理线程单跑（不接取流），测纯推理帧率。如果纯推理已经接近目标帧率，瓶颈在别处；如果远低于目标，先优化模型。

### 2.2 模型侧优化（性价比最高）

| 手段 | 效果 | 代价 |
|:---|:---|:---|
| INT8 量化（已完成） | 4 倍算力 | 少量精度 |
| 换轻量模型（YOLOv5s → YOLOv5n / YOLOv8n） | 帧率显著提升 | 精度略降 |
| 降低输入分辨率（640 → 416/320） | 推理时间约平方级下降 | 小目标漏检 |
| 避免 CPU 算子（上上节的混合调度） | 消除 CPU 瓶颈 | 可能需要改网络 |

**嵌入式类比**：输入分辨率对 NPU 时间的影响就像 ADC 采样率——**翻倍采样率，处理时间约翻 4 倍**（面积增长）。640→416 是很多 IPC 产品的甜点。

### 2.3 数据布局与拷贝

- 输入用 `pass_through=1` + 自己预处理时，确保内存对齐（64 字节对齐对 DMA/NPU 友好）；
- 减少数据拷贝：VPSS 直接输出模型输入尺寸/格式，避免"取大帧再 CPU 缩放"；
- 零拷贝（`rknn_create_mem` 等）在量产场景收益明显，但一代平台支持有限，**以官方文档为准（标注待核实）**。

## 3. CPU 侧优化

### 3.1 找出 CPU 浪费

`top -H` 看各线程。典型浪费：

- 取流线程反复做无谓的格式转换；
- 后处理（解码/NMS）用 Python 实现（慢）；
- 线程之间用大锁同步，导致互相等待。

### 3.2 核绑定

RV1126 四核 A7。把关键线程绑核，避免系统调度抖动：

```bash
# 把 PID 1234 绑定到 CPU0-1
taskset -p 0x3 1234
```

或者在代码里：

```c
#include <sched.h>
cpu_set_t set;
CPU_ZERO(&set);
CPU_SET(0, &set);            // 绑定 CPU0
sched_setaffinity(0, sizeof(set), &set);
```

**布局建议**：取流线程绑核 0，推理线程绑核 1，后处理/显示线程绑核 2，核 3 留给系统。

### 3.3 后处理优化

- Python 后处理改 C（量产必做）：解码 + NMS 用 C 实现，通常能快 3~5 倍；
- NMS 用并行/向量化（简单排序 + 数组操作，避免逐框串行比较太多）；
- 画框等显示操作尽量轻量（只在检测到目标时才画，或隔帧画）。

## 4. 架构侧：多线程流水线

### 4.1 单线程的问题

单线程串行：取帧(10ms) → 推理(20ms) → 显示(5ms) = 35ms/帧 ≈ 28fps 但**延迟 35ms**，且任一段卡顿全链路卡顿。

### 4.2 生产者-消费者流水线

【图1：三线程流水线】

```text
线程A（取流）      线程B（推理）       线程C（显示/后处理）
┌──────────┐ 队列1 ┌──────────┐ 队列2 ┌──────────┐
│ VI 取帧   │─────▶│ 预处理+NPU │─────▶│ 后处理+画框 │
│ 只取帧    │      │ 核心计算  │      │ 显示/推流  │
└──────────┘      └──────────┘      └──────────┘
  生产者            消费者/生产者        消费者
```

> 图1 生图 prompt：三列流水线图，白色背景。三个线程卡片横向排列：左边"线程A 取流：VI 取帧"、中间"线程B 推理：预处理+NPU"（高亮橙色）、右边"线程C 显示：后处理+画框"。卡片之间有两个队列节点（绿色"队列1""队列2"）作为缓冲，箭头从左到右。每个卡片底部标注角色（生产者/消费者）。扁平插画风，比例 16:9，中文标注。

```c
// 伪代码：三线程 + 环形队列（用 POSIX 信号量/互斥锁实现）
// 线程A：取帧入队 q1
while (1) {
    frame = vi_get_frame();
    queue_push(q1, frame);      // 若 q1 满则丢旧帧（策略见下）
}
// 线程B：从 q1 取帧 → 推理 → 入队 q2
while (1) {
    frame = queue_pop(q1);
    rknn_inputs_set(ctx, frame);
    rknn_run(ctx);
    result = rknn_outputs_get(ctx);
    queue_push(q2, {frame, result});
}
// 线程C：从 q2 取 → 后处理 → 显示
while (1) {
    item = queue_pop(q2);
    boxes = decode_nms(item.result);
    draw_boxes(item.frame, boxes);
    vo_send_frame(item.frame);
}
```

### 4.3 队列策略：丢新帧还是丢旧帧

实时视频里，队列满了怎么办？

- **丢旧帧**（推荐）：队列满时 pop 掉最旧的一帧，push 新帧——保证处理的是最新画面，延迟最低；
- **丢新帧**：处理不过来就丢最新的——延迟低但画面跳跃。

**实时监控产品推荐"丢旧帧"**：视觉场景关心"当前画面"，处理旧画面没意义。

### 4.4 双缓冲

推理线程和显示线程**不能同时读写同一帧内存**（会花屏/数据竞争）。用双缓冲（或按帧分配、用完回收）保证同一时刻只有一个线程持有写权限。

## 5. 内存与长期稳定性

| 检查项 | 方法 | 目标 |
|:---|:---|:---|
| 内存泄漏 | 跑 30 分钟以上，`free` 观察 | 内存平稳不增长 |
| 帧泄漏 | 检查每帧是否 Release | 无泄漏 |
| 队列上限 | 环形队列固定大小 | 有界、可预测 |

```bash
# 板端观察内存
free -m
# 长期监控
watch -n 10 free -m
```

## 6. 调优实战顺序（推荐路线）

```text
第一步：测量基线（FPS/延迟/CPU/内存）
   │
第二步：确认瓶颈（纯推理 vs 全链路）
   │
第三步：模型侧（量化→轻量模型→降分辨率）
   │
第四步：架构侧（多线程流水线 + 丢旧帧）
   │
第五步：CPU 侧（绑核 + C 后处理 + 去冗余拷贝）
   │
第六步：再测量，记录前后对比
```

## 7. 练习与里程碑

### 练习

1. **测量基线**：给当前 demo 加上 FPS/延迟/CPU 打印，跑 1 分钟记录基线数据；
2. **纯推理测试**：把取流去掉，单独测 NPU 纯推理帧率，判断瓶颈归属；
3. **分辨率实验**：640 / 416 / 320 三档各测一组 FPS 与检测效果，画一张"分辨率-帧率"表；
4. **流水线改造**：把单线程改成三线程流水线（丢旧帧策略），对比改造前后 FPS 与延迟。

## 8. 小结

- **先测量再优化**：FPS / 延迟 / CPU / 内存四个指标，一次只改一个变量；
- **NPU 侧**：量化（已做）→ 轻量模型 → 降分辨率，模型侧优化性价比最高；
- **CPU 侧**：绑核、C 化后处理、去冗余拷贝；
- **架构侧**：三线程流水线解耦取流/推理/显示，实时场景丢旧帧；
- **稳定性**：帧必须 Release、队列有界、内存不增长。
